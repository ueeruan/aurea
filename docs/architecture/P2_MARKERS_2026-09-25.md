# Marker integrity checkpoint — 2026-09-25

Three shared-core defects were found while checking marker behavior against the
rebuild request:

1. Moving a marker to an occupied frame called `put_marker`, replacing the other
   marker and its label/color. The engine now rejects an occupied destination.
   A stationary drag succeeds without adding a no-op history entry. Undo still
   reaches the preceding real edit.
2. A negative ripple could move later markers before unchanged earlier markers.
   The vector became unsorted, breaking the documented invariant required by
   `lower_bound` insertion and leaving duplicate frames. Stable sorting before
   deduplication restores ordering and preserves the first marker on collision.
3. Reducing FPS could round the last marker to the exclusive composition end:
   frame 59 at 60 fps became frame 30 in a 30-frame composition. Retiming now
   clamps to the valid frame range; label and color remain intact.

Regressions exercise collision plus undo, ripple plus subsequent insertion,
and the 60-to-30 FPS last-frame boundary. Existing marker save/load and retime
coverage remains in `ClipTime.MarkersToggleUndoSaveAndRetime`.

Full host regression passed: **670 tests, 4,135,165 checks, zero failures**,
215.19 seconds. Evidence: `engine/build/host/markers-ctest.log` and
`engine/build/host/Testing/Temporary/LastTest.log`.

These are shared C++ changes used by both platforms. Android arm64 debug build
and Kotlin unit-test task passed (`engine/build/android-p0/gradle-markers-arm64.log`).
iOS scope/resources/effect-contract static checks passed; native iOS compilation
and execution were not performed here.

This does not complete P2. The dedicated marker strip, accessible touch targets,
rename/color/edit UI, drag interaction and full evaluator/graph/gesture acceptance
remain open. The existing iOS bridge does not yet expose marker movement; shared
engine support must not be described as a completed iOS drag interaction.
